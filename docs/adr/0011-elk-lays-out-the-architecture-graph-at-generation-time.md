# ADR-0011: ELK lays out the architecture graph at generation time

- **Status:** proposed
- **Date:** 2026-08-14
- **Deciders:** Hugo Borsoni
- **Tags:** meta, architecture-map, tooling

## Context

The architecture page draws pragma at five levels, and the two diagram levels
that matter most carry 18 and 31 nodes with 18 and 125 edges. The first version
emitted mermaid, which gave no control over whether an arrow could be seen. The
second replaced it with a layered renderer written for this page: longest-path
layering, barycentre ordering, and a cubic bezier straight from each source to
each target.

That renderer draws every edge as a single curve between two boxes and knows
nothing about what sits between them. Measured on the component level in
Chromium, by sampling forty points along each rendered path and testing them
against every node rectangle, **72 of its 125 edges pass through the box of a
node they do not connect**. An edge that runs under an unrelated node reads as
touching it, which is the one thing an architecture diagram must not do: the
whole point of level 3 is to be trusted about what depends on what.

Fixing this is not a tuning problem. Keeping edges out of boxes is the part of
the Sugiyama pipeline this renderer skipped — inserting a dummy node per rank an
edge crosses, reserving a lane for it in the ordering, then routing the edge
through those lanes. That is the expensive half of the algorithm, and it is what
the established layout engines exist to do.

Two constraints close doors before the trade-off starts. The artifact host
blocks every external origin, so anything shipped to the browser is inlined into
the page. And `architecture-graph.ts --check` compares the generated page byte
for byte in pre-commit and in CI, so any layout whose output varies between runs
fails the gate every time.

An earlier commit message in this branch asserted library sizes from a web
search rather than from measurement, and three of the four were wrong. Every
number below was measured on this machine.

## Decision

**Run ELK's layered algorithm inside the generator and ship only the resulting
coordinates.** `elkjs` becomes a devDependency used by
`scripts/architecture/`, never a runtime dependency of the page. The generator
computes node positions and edge bend points at build time and writes them into
the emitted HTML; the browser draws polylines through points that are already
correct, and needs no layout code at all.

The decision that mattered was not which library, but *where layout runs*.
Moving it to generation time takes ELK's routing quality without paying its
weight on every page load, and it keeps the page byte-identical between runs
because the layout is computed once and committed.

## Consequences

- `+` Edges crossing an unrelated node go from **72/125 to 0/125** on the
  component level, measured with the same probe on both.
- `+` The page ships **no layout library**: it stays around 280 KB rather than
  the ~1.9 MB it would reach with `elk.bundled.js` inlined.
- `+` The layout is computed once and committed, so the `--check` byte gate
  needs no tolerance and a reviewer sees layout changes in the diff.
- `+` ELK packs tighter than the alternative: 2926×709 against dagre's
  2980×1982 for the same graph, so less scrolling.
- `-` A new devDependency of 1.6 MB installed, and ELK is GWT-compiled Java,
  which nobody here will debug if it misbehaves. The mitigation is that it runs
  only in the generator, so a failure is a build error rather than a broken
  page.
- `-` The layout can no longer react to the viewport. It is computed for one
  canvas size, and the page pans and zooms over it rather than reflowing. For a
  fixed diagram this is what we want anyway.
- `~` Bend points are written to the committed HTML, so a node rename that
  shifts the layout produces a larger diff in the generated file than before.
  The file is already in `.prettierignore` and is regenerated by a gate, so no
  one edits it by hand.

## Alternatives considered

### Option A — ELK at generation time (chosen)

- **Summary:** `elkjs` runs in `architecture-graph.ts`, which emits nodes with
  absolute positions and edges with bend points. The browser renderer keeps its
  hover, pin, pan and zoom behaviour and loses only its layout code.
- **Strengths:**
  - Zero edges through unrelated nodes, at all three ELK routing modes
    (`ORTHOGONAL`, `POLYLINE`, `SPLINES`) — measured 0/125 on each.
  - Nothing added to the page payload.
  - Deterministic: five consecutive runs produced byte-identical output.
  - Smallest canvas of the three engines measured. All four of ELK's node
    placement strategies reach zero crossings, so the choice among them is
    area: `SIMPLE` gives 2926×709 against `BRANDES_KOEPF`'s 3007×1087, and
    ships.
- **Costs:**
  - 1.6 MB devDependency (`elk.bundled.js`, 470 KB gzipped), install-time only.
  - Generation gets slower by roughly the cost of one ELK pass per level.
- **Rationale:** It is the only option that reaches zero crossings, and running
  it at build time removes its single real drawback.

### Option B — dagre in the browser (rejected)

- **Summary:** Inline `@dagrejs/dagre` (48,956 bytes minified, 17,119 gzipped)
  and lay out on load.
- **Strengths:**
  - Genuinely small — 18% of the current page, the only engine that could be
    inlined without dominating it.
  - Deterministic, so the byte gate is safe.
  - Real routing: 5.7 bend points per edge on average, from real dummy nodes.
- **Costs:**
  - **33–36 of 125 edges still cross an unrelated node** (26–29%), measured at
    two spacings with true per-node widths. Better than 72, nowhere near zero.
  - Canvas roughly twice as tall as ELK's for the same graph.
- **Rejection rationale:** It loses on the one criterion that triggered this
  work. Halving a defect that makes the diagram lie is not fixing it. If page
  weight were the dominant criterion this would win outright, and it remains the
  fallback if the ELK devDependency ever becomes a problem.

### Option C — ELK inlined into the page (rejected)

- **Summary:** Ship `elk.bundled.js` inside the generated HTML and lay out on
  load, as the artifact CSP requires of any runtime library.
- **Strengths:**
  - Identical routing quality to Option A.
  - Layout could adapt to viewport width.
- **Costs:**
  - Takes the page from ~280 KB to ~1.9 MB, a sevenfold increase, for a
    capability the reader never sees run.
  - Every regeneration rewrites 1.6 MB of vendored library text inside a
    committed file.
- **Rejection rationale:** It pays the full weight for a computation whose
  answer never changes between loads. Viewport-adaptive layout is not worth
  1.6 MB on a diagram that pans and zooms.

### Option D — keep the hand-rolled renderer and add obstacle avoidance (rejected)

- **Summary:** Implement dummy-node insertion and lane routing in the existing
  ~200-line renderer.
- **Strengths:**
  - No dependency at all.
  - Full control of the drawing.
- **Costs:**
  - This is the hard half of Sugiyama. Writing it, and keeping it correct across
    cycles, multi-rank edges and ports, is a genuine project.
  - Every future defect is ours to find, with no upstream and no test suite.
- **Rejection rationale:** Loses on effort and on risk against a measured 0/125
  available from an established engine. The first two attempts at this renderer
  already shipped defects found only by rendering and looking; a third, harder
  attempt is not the way to spend the time.

## Evaluation rubric

| Criterion | Weight | Why it matters |
|---|---|---|
| Edges never cross unrelated nodes | high | A diagram that implies a dependency that does not exist is worse than no diagram; this is the defect that opened the ADR |
| Deterministic output | high | `architecture-graph.ts --check` compares the page byte for byte in pre-commit and CI |
| Page payload | medium | The artifact CSP forces inlining, so a runtime library is paid on every load |
| Maintenance surface | medium | One developer; code we write is code we debug alone |
| Layout compactness | low | Affects scrolling, not correctness |

|  | A: ELK at build | B: dagre in browser | C: ELK in browser | D: hand-rolled |
|---|---|---|---|---|
| No crossings | ✓ 0/125 measured | ✗ 33–36/125 | ✓ 0/125 | ✗ 72/125 today, unknown after work |
| Deterministic | ✓ 5 runs identical | ✓ layered, no RNG | ✓ same engine | ✓ no RNG |
| Page payload | ✓ nothing added | ~ +49 KB | ✗ +1.6 MB | ✓ nothing added |
| Maintenance | ✓ upstream owns layout | ✓ upstream owns layout | ✓ upstream owns layout | ✗ we own the hard half |
| Compactness | ✓ 2926×709 | ✗ 2980×1982 | ✓ 2926×709 | ~ not measured |

## Implementation pointers

- Files: `scripts/architecture/architecture-layout.ts` holds the ELK pass;
  `architecture-graph.ts` calls it per level and writes positions into the
  payload; `architecture-graph-view.ts` lost `layoutGraph` and now only draws
  and handles interaction.
- Result after the change, measured with the same probe on the rendered page:
  context 0/15, container 0/18, component 0/125.
- Measurement: the crossing probe samples forty points along each rendered path
  and tests them against every node rectangle, ignoring the two endpoints' own
  boxes and the first and last few units of arc length.
- Sizes measured with `npm install` then `stat -c%s` and `gzip -c | wc -c`:
  `dagre.min.js` 48,956 (17,119 gz); `elk.bundled.js` 1,609,707 (469,661 gz);
  `cytoscape.min.js` 435,503 (136,809 gz); `vis-network.min.js` 435,001
  (124,426 gz).
- Related ADRs: none. This is the first decision about the architecture map.

## The options, and what they were measured against

These numbers are why the layout options are what they are. Nothing in the code
can recompute them, and each was taken on the component level of the real graph.

- **`nodePlacement`: `SIMPLE`, not `BRANDES_KOEPF`.** All four placement
  strategies reach **zero edge crossings** here, so crossings do not decide it
  and area does: `SIMPLE` gives **2926 x 709**, `BRANDES_KOEPF` **3007 x 1087**.
- **`edgeRouting`: `POLYLINE`, not `SPLINES`.** `SPLINES` reaches the same zero
  crossings and emits roughly **three times the points**, which is page weight
  for no readability gain.

## The text-width constants are measured, not guessed

Label boxes are sized from a per-character width because the layout runs before
a browser exists. The constants come from `getComputedTextLength` in the page:
**9.016 px per character** for a node name at its 15 px weight, and **6.315 px**
for the lines beneath it. The code carries 9.3 and 6.5 — the measured figures
plus headroom, so a slightly wider glyph set does not overflow the box.
