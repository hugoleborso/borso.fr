# S3 + Origin Access Control hides "missing" inside "forbidden"

## User impact

A visitor who mistyped a URL on any prod or preview site saw CloudFront's bare
"Access Denied" page, HTTP 403, instead of the site's `/404.jpeg` page. Every
missing path did the same, found on the first broken-link click after deploy.

| | Seen | Expected |
| --- | --- | --- |
| `https://borso.fr/typo` | 403 "Access Denied" XML page | 404 with `/404.jpeg` |

## Causal chain

- The visitor saw CloudFront's "Access Denied" page for a missing path.
  - CloudFront forwarded S3's 403 verbatim. Its `errorResponses` had a rule for
    404 only.
    - S3 answered 403 for the missing key. A caller without `s3:ListBucket`
      gets 403 whether the key is missing or forbidden.
      - The bucket policy granted the CloudFront principal `s3:GetObject` only.
        `S3BucketOrigin.withOriginAccessControl(bucket)` grants read access
        unless `originAccessLevels` asks for more.

        ```ts
        origin: S3BucketOrigin.withOriginAccessControl(bucket), // ← ❌ READ only: missing keys answer 403
        // …
        errorResponses: [{ httpStatus: 404, responsePagePath: '/404.jpeg' }], // never reached
        ```

        - `StaticSite` was written with the 404 rule beside the default OAC
          origin, the setup of a public bucket, where S3 answers 404 for a
          missing key.

## Root cause of occurrence

*Thought S3 behind Origin Access Control answers 404 for a missing key, as a
public bucket does, actually with read access only it answers 403 for a missing
key and a forbidden one alike, so a 404 error page is unreachable.* (Material)

The writer was an agent. The answer was in CDK's own README for
`aws-cloudfront-origins`: "By default, S3 origin returns 403 Forbidden HTTP
response when the requested object does not exist. When you want to receive 404
Not Found, specify `AccessLevel.LIST` in `originAccessLevels` to add
`s3:ListBucket` permission in the bucket policy." That README was not in the
agent's context when it wrote the construct (inferred: the fix wrote a custom
policy statement instead of the documented option).

## Detection failure causes

- **Typing:** `withOriginAccessControl(bucket)` and a 404 `errorResponses` rule
  type-check together. Nothing ties the error rule to the access level.
- **Linter:** no rule relates an OAC origin to its error responses.
- **Local validation:** the happy path and the distribution config were tried,
  not a missing key.
- **CI:** synth tests asserted the template's structure, and no test asserted
  the bucket policy's actions.
- **Monitoring:** no alarm on the 403 rate.

## Countermeasure

16fde654f adds a `s3:ListBucket` statement for the CloudFront service principal
in `StaticSite`, scoped by `aws:SourceArn` to its own distribution. 0f36781ae
does the same on the shared previews bucket and adds a 404 error response on
the previews CDN, served from one bucket-root `404.jpeg`, uploaded once by the
operator. A 403-to-404 remap was rejected: it loses the forbidden or missing
distinction and still shows CloudFront's page when the JPEG is absent.

## Eradication

**Type:** detection (level 4)

**Reference:** commits [`16fde65`](https://github.com/hugoleborso/borso.fr/commit/16fde65)
and [`0f36781`](https://github.com/hugoleborso/borso.fr/commit/0f36781),
[PR #2](https://github.com/hugoleborso/borso.fr/pull/2).

```diff
+ bucket.addToResourcePolicy(new PolicyStatement({
+   actions: ['s3:ListBucket'],
+   principals: [new ServicePrincipal('cloudfront.amazonaws.com')],
+   resources: [bucket.bucketArn],
+   conditions: { StringEquals: { 'aws:SourceArn': distribution.distributionArn } },
+ }));
```

What holds today: `static-site.test.ts:93` and `shared-stack.test.ts:200` assert
the grant on their own construct. The 2026-05-02 entry claimed level 1 because
"every CloudFront-fronted S3 bucket in the repo lives inside `StaticSite` or
`SharedStack`". That stopped holding on 2026-05-15. `PhotosCdn` (b80a866b4)
added a third OAC origin, `infra/cdk/src/constructs/photos-cdn.ts:71`, with no
`s3:ListBucket`, so a missing photo answers 403. A new distribution can add an
OAC origin without the grant and no check sees it.

**Proposed:** subtract the two hand-written statements. Add one helper in
`infra/cdk/src/internal/` that returns
`S3BucketOrigin.withOriginAccessControl(bucket, { originAccessLevels: [AccessLevel.READ, AccessLevel.LIST] })`,
the option CDK documents for this exact case. `StaticSite`, `PhotosCdn` and
`SharedStack` (which already imports `@borso/infra`) call it and delete their own
policy code. Then a rule under `eslint-rules/` refuses
`withOriginAccessControl` outside the helper, so no distribution can get an OAC
origin that answers 403 for a missing key. Whether the CDK option scopes the
grant to the distribution as the current `aws:SourceArn` condition does is
unverified. None of this exists yet.

**Proof it can fail:** not run.

**Similar instances:**
`grep -n "withOriginAccessControl" infra/cdk/src/constructs/*.ts infra/shared/lib/*.ts`
finds three origins: `static-site.ts:109` and `shared-stack.ts:104`, both
granted, and `photos-cdn.ts:71`, not granted.
