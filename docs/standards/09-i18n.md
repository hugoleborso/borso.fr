# 09. Internationalisation

## Rule

Every string a user reads comes from a translation catalogue through
`react-i18next`, and no user-facing string is written inline in a component.
Every application ships an English catalogue and a French catalogue, and the
two have exactly the same keys.

## Reason

The rule that all code is written in English, from
[01. Naming](./01-naming.md), needs somewhere for French text to live, and the
catalogue is that place. Without it, French labels end up inline, and then
identifiers drift into French too.

Catalogues also make missing text visible. A key with no translation shows the
key itself, which someone notices, whereas an inline string that only exists in
one language shows nothing wrong until a French speaker reads the page.

## Setup

Each application has an `i18n` folder holding the catalogues and the
initialisation:

```
site/src/i18n/
  en.json
  fr.json
  i18n.ts                    initialises i18next
  i18n.utils.ts              pure helpers, e.g., picking the initial language
  locale-storage.utils.ts    reads and writes the saved choice
  i18n-parity.core.ts        compares the two catalogues
  i18n-parity.core.test.ts   fails when the catalogues disagree
  react-i18next.d.ts         types the keys from en.json
```

`react-i18next.d.ts` is what makes a wrong key a compile error:

```ts
import type english from './en.json';

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: { translation: typeof english };
  }
}
```

## Key naming

A key is a dotted path from the screen to the element, in lower case with
hyphens inside a segment. The path describes where the string appears and not
what it says, because the text changes and the location does not.

```json
{
  "catalog.page-title": "Catalog",
  "catalog.empty-state.title": "No songs yet",
  "catalog.empty-state.action": "Add your first song",
  "common.action.save": "Save",
  "common.action.cancel": "Cancel"
}
```

Strings that appear on several screens live under `common.`, and everything
else lives under the name of its route.

Do not build a key by concatenating strings at runtime, because the parity test
and the type checker both stop working when you do. Write a lookup from the
domain value to a literal key instead, in a `.core.ts` file.

## Plurals and interpolation

Use i18next plural suffixes rather than a condition in the component:

```json
{
  "leaderboard.lap-count_one": "{{count}} lap",
  "leaderboard.lap-count_other": "{{count}} laps"
}
```

Numbers, dates, and durations go through `Intl` inside a `.utils.ts` formatter,
which takes the locale as an argument so it stays pure.

## Choosing the language

The initial language comes from the saved choice, then the browser languages,
then English. The decision is a pure function taking both inputs, so it has
tests:

```ts
export function selectInitialLanguage(
  savedLanguage: string | null,
  browserLanguages: readonly string[],
): SupportedLanguage { … }
```

The language switcher is a molecule, and it writes the choice to
`localStorage` and calls `i18n.changeLanguage`.

## Catalogue parity

`i18n-parity.core.ts` compares the key sets of the two catalogues and returns
the keys that are missing on each side, and the sibling test fails when either
list is non-empty. The check runs in the normal Vitest suite, so a pull request
that adds an English string without the French one does not merge.

## Enforced by

- `eslint:borso/no-literal-jsx-text` rejects visible text in JSX that does not
  come from `t()`, with an allowance for punctuation and numbers.
- `eslint:borso/no-dynamic-translation-keys` rejects a template literal or a
  concatenation passed to `t()`.
- `test:i18n-parity.core.test.ts` fails when the two catalogues disagree on a
  key.
- `types:react-i18next.d.ts` declares `CustomTypeOptions`, which turns an
  unknown key into a compile error.
- `reviewer` checks that a key's dotted path names the screen and the element,
  so the catalogue stays readable as it grows.
