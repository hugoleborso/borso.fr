## Notes

- **Row 12, FAIL.** On the dev server the transition popup cannot be opened. It is added, closed 2 ms later and removed 4 ms later (measured, trace above), with no click in between. The same tree works on a production build (rows 13 to 18). Cause, inferred from the diff and the trace: this branch makes `openDialogOnAttach` return `() => dialog?.close()`. In development React 19's `StrictMode` (`apps/pragma/site/src/main.tsx:46`) runs every ref callback, then its cleanup, then the callback again. The cleanup's `close()` fires the popup's `close` event, `onClose={close}` in `SceneTransitionStrip.tsx` sets `isOpen` to false, and React removes the dialog. The stage survives only because `openSceneOnAttach` drops the cleanup, which the technical review flags as A13. Anyone working on Scene Mode under `pnpm dev`, and any validator pointed at the dev URL, sees the transition strip do nothing. A dialog's cleanup has to survive a detach followed by a re-attach, for example by not closing it, or by ignoring a `close` that follows a re-attach. That decision belongs to the fix, not to this report. Whether the popup opened on dev before this branch was not run. It is inferred from the old adapter, which returned nothing, and from PR #380's validators, who opened it.
- **Row 05, UNVERIFIABLE.** Row 15's rationale says a practice today "would erase Hugo's seeded open-today flame". Hugo reads 5 days, counted today, after both seeds. Reading a flame needs a sign-in, and the sign-in may itself count today, so a Hugo flame still open today could not be observed. Row 04 does confirm the practice lights Marc's and Sarah's flames.
- The run reseeded the shared dev database three times through `POST /api/__test/seed`. It ended on a plain seed, so the dev database holds the default fixture and every id from earlier runs is gone.

## Verdict: FAIL
