## Notes

- The spec's API table says `POST /` takes "(2 to 8)" players, while *Screens* and *Rules* say three to eight and the code enforces three. Should the table read 3 to 8?
- Moving the phase back across rounds (`PUT /phase {round: 1, phase: 'bidding'}` from round 3) keeps the `round` and `round_entry` rows of rounds 2 and 3. Moving forward again brings their old bids, tricks and Kraken flags back. The site's prediction drops those rounds (`it('drops the rounds after the one it moves back to')`, game-edits.core.test.ts:125). No screen moves back more than one step today. Is the server meant to keep those rows?
- `startRematch` inserts the new game before it claims `rematch_join_code`, so every losing concurrent request leaves an unreachable game, its `join_code_claim` row and its players behind (measured: three concurrent requests all answered one code; inferred from games.service.ts:257-267, not counted in the table: two orphaned games). Is that cost accepted?
- Several C03 survivors look equivalent (for example `scoring.core.ts:88`, where `selectTricksTaken` can return `null` only when the bid is `null`). The gate still fails on them. Each needs a restructure or a test, per `docs/knowledge/how-a-mutation-survivor-hides.md`.
- `VOCABULARY.md` › Phase says "A phase moves forward only when every bid is placed and every played round balances". That stops being false once E05 is fixed, so it has no row of its own.
