## Notes

- **A15**: Spec *Result 2* and *Happy path 3* ("They raise their score from 5 to 7"). `StudyQueue.tsx:46-48` computes each step as `stepScore(row.score, direction)`. `row.score` comes from the overview query. `useSaveSongScore` (`studies.queries.ts:134-150`) is pessimistic, with no `onMutate`, and refreshes the overview only through `invalidateQueries` in `onSuccess`. Nothing disables the − / + buttons while the write is pending (`StudyRow.tsx:55-81`). So a second tap before the PUT and the overview GET both return sends the same value again: from 5, two taps send `score: 6` twice. The score ends at 6, not 7, and `mastery_score_change` gets two identical rows. This is read from the code, not observed. `/visual-validation` can confirm it with two `scripts/argent.sh` taps on a preview. Two fixes, either enough: step from the cache by patching the queue row's `score` in an `onMutate`, then settle from the PUT response (the matrix's `useSaveMasteryDefault` already does this); or disable the stepper while `saveScore.isPending`.
- **A43**: The spec's *Zero-defect strategy* table promises three alerts: first occurrence of `study-not-in-lineup`, more than 10 per hour of `study-not-found`, and first occurrence of `mastery-history-write-failed`. It also promises an info log for `study-not-found`. Nothing in the diff produces any of them, and the repository has no log-based alerting to hook into: no `MetricFilter` exists under `apps/*/cdk` or `infra/`. The *Analytics* section was amended at implementation to what the request log can actually answer. This table was not, so it describes a protection nobody can observe, which CLAUDE.md's last *Don't* forbids. Either add a metric filter and alarm on the request-log lines (`POST /api/studies 422`, `DELETE /api/studies/… 404`, `PUT /api/mastery/overrides 500`), or amend the table to "visible in the Lambda request log; no alert yet", the same way the Analytics paragraph was amended.
- **Observed, not counted as FAIL**: `useSaveMasteryDefault` (`site/src/lib/queries/mastery.queries.ts:29-53`) does not touch `['studies', 'overview']`. A default score changed in the matrix therefore reaches the Studies tab's readiness only when the 30 s `staleTime` (`query-client.setup.ts:3`) expires. The plan's *score change moves readiness* row named only the override mutation, and the spec's Happy path 3 uses the Studies tab's own stepper, which does invalidate.
