## Notes

- **A27 FAIL (logging contract).** The spec's *Zero-defect strategy* says "`CalendarFeedNeedsReconnecting` and `CalendarFeedUnavailable` are logged with `memberId` and the status code". `calendar-feeds.service.ts:60` logs `{ event, memberId }` with no status code. The adapter's `FeedReadOutcome` (`{ kind: 'needs-reconnecting' }` / `{ kind: 'unavailable' }`) drops the status before the service sees it. The spec's *Analytics* line says `free_slots_computed` carries "the counts of feeds read, failed and excluded, and the duration". The log at `free-slots.service.ts:26-34` carries `members`, `feedsRead`, `excluded`, `slots` and `durationMs`, and no failed count. `excluded` mixes `no-calendar` with feed failures, so the failed count cannot be read back from it. The event names are also snake_case (`calendar_feed_needs_reconnecting`) where the spec names `CalendarFeedNeedsReconnecting`. That is cosmetic, but the CloudWatch query the operator writes from the spec would not match. Fix: carry the status in the failure outcome and log it, and add `feedsFailed` to `free_slots_computed`. The alternative is to amend the spec.
- **D03 FAIL (crossing midnight).** The spec's test strategy lists "events crossing midnight" for `free-slots.core.ts`, and the edge case says such an event "blocks both evenings it touches". The implementation subtracts every busy interval from each window independently, so the behaviour is probably right. But no test feeds `selectFreeSlots` or `subtractBusyIntervals` an interval such as 22:30 → next day 19:30 Paris across two consecutive windows and asserts that both are cut. Add that case to `free-slots.core.test.ts`.
- **D16 FAIL (timeout).** The spec's back-e2e bullet says "a timeout gives 'unavailable'". The back-e2e uses a 503, which covers the 5xx row and not the timeout. The adapter test passes `timeoutMs: 1`, but its fetcher rejects at once whatever the signal does. Removing `signal: request.signal` from `calendar-feed.adapter.ts:86` would keep every test green, and Stryker has no mutator for dropping an object property. The `slow.ics` fixture (6 s against a 4 s limit) is exercised only through `answerFixtureFeedRequest` returning `delayMs`. Fix: an adapter test whose fetcher resolves only when `init.signal` aborts, with a small `timeoutMs`, asserting `{ kind: 'unavailable' }`. A back-e2e variant would also satisfy the spec's wording.
- Observation, not scored: the first `test:coverage` run on pragma failed 11 back-e2e tests with `duplicate key value violates unique constraint "member_credential_username_idx"` and `"app_config_pkey"`. Two commits (`b09e961`, `ae9fd82`) landed on the branch during that run, and the shared `/tmp/borso-pg-pragma` cluster had been running since 11:25, which points to another process using it at the same time. A clean re-run at `ae9fd82` passed 2205/2205, and C02 reports that run. Logged to the kaizen log.
- Observation, not scored: `test-seed.service.ts` `seedCalendarFeeds` uses `memberIdByName.get(seed.firstName) ?? ''`. A renamed seed member would then try to insert an empty string as a uuid instead of failing with a clear message. This is test-only code.
- Observation, not scored: the plan names `sessions.schema.test.ts` as the self-check for `origin`. No such assertion exists. `origin` is covered at `sessions.core.test.ts:30` (`'keeps only the prepared concert and the origin for a practice'`), and the schema's refusal of any other value is not tested. The use case itself (step 6) is routed to visual validation.
