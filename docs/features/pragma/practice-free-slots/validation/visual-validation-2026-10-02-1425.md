## Notes

- **32 FAIL (a redirect to a loopback target is accepted at save time).** The error case says an address that "redirects to one [an IP literal or `localhost`] … is rejected at save time and again when the feed is read". Both `https://httpbin.org/redirect-to?url=https%3A%2F%2F127.0.0.1%2Fa.ics` and the same with `localhost` were saved as "Calendar connected". The read-time guard then excludes the member as `unavailable` (row 33), so nothing behind the redirect was reached. Either the save probes the address and checks its redirects, or the spec sentence should say that redirects are checked only when the feed is read; as written, the screen does not match it.
- Observation on row 33, not a verdict: `127.0.0.1.nip.io` and `localhost.localdomain` are accepted at save time. They are DNS names, which the spec leaves to the read-time check. At read time `127.0.0.1.nip.io` gives `unavailable` in about 300 ms; from the browser, a guard refusal and a refused connection to port 443 on loopback look the same.
- Observation on rows 06 and 09, not a verdict: `session.origin` is not returned by any API response, so the stored value was read from the request body and the enum validation, not from the database. The first `GET /api/sessions` after each create (both the click and the argent tap) did not list the new practice; the next read did. This is the known DSQL read-after-write behaviour.
- Environment: the first `POST /api/__test/seed` of the run returned `500 Internal Server Error`; the retry returned 200. After the second seed, the signed-in browser kept showing the app shell while `/api/free-slots` answered 401 `bad-signature`, and the block showed "The free slots could not be computed."; signing in again fixed it.

## Verdict: FAIL
