## Notes

- Behaviour 2 invalidates every query whenever a hidden tab is shown again, and 8 rules plus every MCP write send `all` (stale-scope.core.ts:20-36). `docs/dantotsus/five-musicians-filled-ten-lambdas.md`, part of this pull request, traces 402 throttled invocations to refetch bursts against a reserved concurrency of 10. Does a phone unlock, or one song edit, now make every other open tab refetch every active query at once, and has anyone counted those requests against that limit? The spec mandates both behaviours, so this is a question for the operator, not a finding.
- Every write now holds its API Lambda until the broadcast settles, up to 1500 ms (app.ts `STALE_BROADCAST_BUDGET_MILLISECONDS`). The ADR marks that budget as a choice, not a measurement. Does that extra occupancy matter under the same concurrency limit?
- A tab's first socket open invalidates nothing (live-invalidation.core.ts:213). A write landing between that tab's first fetch and its `$connect` row is never announced to it, so the tab keeps that data until the 5-minute freshness runs out. Is that window acceptable?
- `onToolRan` runs in a `finally` (mcp-server.adapter.ts:56-57), so a write tool that failed still sends `all`. This over-invalidates and does not under-invalidate.
- `/api/me/contact` sends `members` and `/api/me/calendar-feeds` sends `free-slots`, while `GET /api/me` (key root `me`) shows the member's own contact and calendar feeds. The same member's other device keeps its profile screen stale. Does the spec mean "other members" only?
- In `main.dev.ts`, a rejected `$connect` promise (local database down) is unhandled, and the matching `$disconnect` never runs. This is development only.
- The preview clones production's `app_config` HMAC key (ADR-0009), so a ticket minted on a preview verifies on production's `$connect`, just as a session cookie already does. Nothing new is exposed, since the socket carries only scope names.
