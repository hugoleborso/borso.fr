# Plan — The room picks the next song

> Early quality check. Pair with [`../spec/spec.md`](../spec/spec.md). When a defect lands and a Dantotsu traces back here, the chain is visible: the plan either named the risk and we missed mitigating it, didn't name the risk at all (planning gap), or named it correctly and the defect comes from elsewhere.

One decision behind this feature is ratified and committed on this branch, and every row below whose decision comes from it links it: [ADR-0015](../../../../adr/0015-musicbrainz-stays-the-song-search-source.md) for the song-search source. [ADR-0016](../../../../adr/0016-qrcode-react-for-the-audience-vote-qr-code.md) chose a QR-code library and is now deprecated: the QR code was withdrawn, so this feature adds no third-party dependency.

## Pattern coherence pass

| Question | Answer | Where it lands |
|---|---|---|
| Does this feature add a dependency the spec does not justify? | No dependency at all. The one candidate, a QR-code encoder, went away with the QR code itself. | `pnpm-workspace.yaml` catalog, `apps/pragma/package.json` |
| Does it introduce a state pattern that duplicates an existing one? | No. Polling goes through `refetchInterval`, which `query-polling` already establishes. The ballot token is a local-storage adapter, which `session-marker.adapter.ts` already establishes. | `lib/queries/audience.queries.ts`, `lib/ballot-token.adapter.ts` |
| Does a new pattern absorb an old one? | The MusicBrainz cache moves from module state into a table, so the module-level `Map` and its TTL eviction helper are removed rather than left beside the new cache. Two caches for one query would be the failure. | `songs/musicbrainz.adapter.ts`, `songs/musicbrainz.core.ts`, `songs/search-cache.repository.ts` |
| Does the countdown need a second clock store? | Yes, and the existing one cannot be widened. `clock.store.ts` ticks once a minute and several screens read it; making it tick every second to serve one countdown would wake every subscriber sixty times more often for the whole application's life. | `components/molecules/vote-countdown.store.ts`, a second external store whose interval runs only while it has subscribers |

## Mount-time contract

The vote page mirrors one piece of client state to an external system on first paint. Nothing else in this feature does.

| State | External system | Call | History mode | When |
|---|---|---|---|---|
| Ballot token for this concert | Browser local storage, key `pragma.ballot.<sessionId>` | `localStorage.getItem` on first render through `readBallotToken(sessionId)`; `localStorage.setItem` through `writeBallotToken(sessionId, token)` only after `POST /ballot` answers | N/A | The read happens during the first render of the organism that owns the state query. The write happens after the mint response, never speculatively, so a failed mint leaves no token behind that the server does not know. |
| Short address resolution | The browser history entry | `navigate('/vote/' + sessionId, { replace: true })` from `VotePage` when the short address resolved to a concert | replace | Once, after `GET /api/audience/live` answers with a session id. Replace rather than push, so the back button leaves the site instead of bouncing between `/vote` and `/vote/:id`. |

## Risk register

| Risk | Severity | Mitigation in plan | Detection if it slips |
|---|---|---|---|
| A gated audience route is mounted in a way that gates the public routes too, or a later edit reorders the two `.route` calls and the whole public surface starts answering 401 | high | The gate is applied per route rather than through `.use('*')`, which makes the mount order irrelevant. Public is still mounted first, so both defences are in place | The ungated-access controller test drives every public route through `createApp()` with no cookie. It fails loudly on a 401. Without that test the failure reaches the room at the concert, where nobody can debug it. |
| The reverse: a route meant to be gated is left public because the per-route middleware was forgotten on one of the two gated routes | high | Both gated routes carry `requireSharedPasswordSession` as their first handler argument, and the same test asserts 401 on both with no cookie | The same test. A gated route answering 200 without a cookie fails it. |
| Two concurrent state reads both settle the same round, appending two setlist entries for one winner | high | Settlement is claimed with a conditional update on `settled_at IS NULL`, and only the claimer appends. The claim and the append share one transaction | The concurrent back-e2e test firing two `GET /state` with `Promise.all` and asserting exactly one entry. In production, a round whose winner appears twice in the setlist is the visible symptom, and `audience_round_settled` firing twice for one round id is the logged one. |
| The settlement transaction commits the claim and fails the append, leaving a round marked settled with a winner that is in no setlist | medium | The two writes share one transaction lent out by the setlists slice, following `repository-owned-transaction`, so neither can commit alone | A back-e2e test that makes the append fail and asserts `settled_at` is still null. In production, a round with `winning_song_id` set and no matching setlist entry is the query to run. |
| DSQL aborts the loser of a concurrent write at commit with a serialization failure, and the service reports it as a 500 rather than as the conflict it is | medium | The service catches the serialization failure on both the round-open path and the settlement path and converts it to the same outcome the sequential case produces: 409 for a second round, and a re-read for settlement | The concurrent back-e2e tests assert 201 and 409, never 500. In production, any 500 on `POST /rounds` or `GET /state` is this. |
| `setlist_sheet.kind` is null on every row that existed before the migration, and a read path assumes a value | medium | The narrowing defaults to `'manual'` in one place, `resolveSetlistKind` in `setlists.core.ts`, called from the repository row mapper so no read path sees the raw column | `setlists.core.test.ts` covers the null branch. A back-e2e test reads a setlist created before the column existed, seeded with `kind` left null, and asserts it reads back as `manual`. |
| A future `drizzle-kit generate` emits `ALTER COLUMN ... SET NOT NULL` for `setlist_sheet.kind` because someone added `.notNull()` to the Drizzle column | medium | The column carries neither `.notNull()` nor `.default()`, and the plan says why in the row above | `./scripts/check-migration-sql-dsql-compat.sh` rejects the statement at pre-commit, before it can reach a preview deploy. |
| The countdown drifts or freezes because the one-second store keeps an interval alive after the last subscriber leaves, or fails to start for a late one | medium | The store follows `external-store-module`: the interval starts on the first subscriber and is cleared on the last, exactly as `clock.store.ts` already does | A component test mounts and unmounts the countdown and asserts the interval was cleared. A leaked interval shows up as the jsdom suite refusing to exit. |
| The visitor's browser polls once a second for the whole concert because the round-open check is wrong, and the Lambda bill and DSQL connection count grow with the room | medium | `refetchInterval` is derived from the last response and is `false` whenever no round is open | A back-e2e or component test asserting the interval is `false` at rest. In production, `audience_ballot_minted` staying flat while request volume climbs is the shape. |
| The search cache write races between two Lambdas resolving the same cold query and one of them fails the request | medium | The cache write is an idempotent upsert on the provider-namespaced query key, following `repository-idempotent-upsert`, and a failed cache write never fails the search that produced the hits | A back-e2e test writing the same cache key twice and asserting no error. [ADR-0015](../../../../adr/0015-musicbrainz-stays-the-song-search-source.md) already records this as a known cost of moving the cache into DSQL. |
| The `adapter-rate-limited-fetch` blueprint keeps describing a module-state cache and a silent empty result after both are gone, and the next adapter copies the old shape | medium | The blueprint description is rewritten in the same commit that changes the mechanism | `./scripts/reports.sh blueprints` then reading the row. Nothing automated compares a description to its code, so this one is a human read and is listed as a `human:` gate. |
| The visual validation run reuses the band's browser profile, so the public page is tested with a session cookie and the whole point of the feature goes unverified | high | The spec already requires a context with no session cookie. The plan restates it as a named gate | The visual validation report must include a screenshot of the public page taken in a context where `document.cookie` carries no session, and must state that it did. A report that does not say so is treated as not having done it. |
| The thirty-second waits make the visual validation run flaky on a slow machine | low | Accepted in the spec as the cost of not adding a duration parameter | The visual validation report's own pass or fail. The spec says to revisit if the run gets flaky, so a second flaky run is the trigger to re-open Q13, not a reason to add the parameter quietly. |

| Ballot fraud is described somewhere as prevented | low | The spec's wording is carried into the plan and must be carried into the pull request: this is a bar, not an election | A read of the pull request body before it is opened. |

## Decisions taken while planning

These are recorded here rather than under open questions, because each was settled and none blocks implementation. They are listed so a later Dantotsu can find them.

- The short address needs an endpoint the spec's API table does not list. `GET /api/audience/live` is added, public, answering `{ sessionId: string | null }`. The behaviour it serves is ratified; only its shape was missing.
- `resolveSetlistKind` moves from `setlists.schema.ts`, where the spec put it, into the existing `setlists.core.ts`, because `borso/pure-functions-live-in-core-files` treats only `.core.ts` and `.utils.ts` as pure files.
- The gated audience routes apply their guard per route rather than through `.use('*')`, which removes the mount-order hazard measured above.
- A tie that survives both the vote count and the earliest latest vote is broken on `songId` ascending, so the pure settlement function is total.
- `songs.controller.ts`, `songs.service.ts`, `songs.queries.ts` and `SongSearch.tsx` join the change set, because the search return type that ADR-0015 changes is shared with the existing gated search route.
- The countdown gets its own one-second store rather than speeding up `clock.store.ts`, which several screens read at one minute.

## Open questions / unknowns

None. The spec settles the product surface, the two ADRs settle the decisions that reached beyond it, and the six items above were engineering choices this plan was entitled to take.

## Missing technical skills

- **A DSQL concurrency skill.** Three of the high and medium risks above are the same shape: a write that two callers can reach at once on a store that resolves conflicts at commit rather than by locking. The plan reasons it out each time from ADR-0006 and the compatibility page. A `.claude/skills/dsql/` skill holding the conditional-claim pattern, the serialization-failure handling and the transaction ceiling would make that reasoning reusable instead of rediscovered.
- **A public-surface skill.** This is the first unauthenticated write path in `pragma`, and the checks it needs are not obvious: the ungated-access test through the composition root, the rate limiter, the token that is opaque and never derived from the person, and the browser context with no session cookie during validation. The next public surface in any application here will need the same list.
