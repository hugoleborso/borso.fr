## Notes

- **Row 08 (FAIL — reset-to-default UX diverges from spec).** The spec walks through a two-step reset: (2) reset returns the form to song-default values _with the modal still open and no save yet_; (3) the user reviews, then clicks Save to clear the override. The implementation collapses that into a one-click flow — clicking "Reset to song default" calls `onReset()` (which fires the `{ lineupOverride: null }` mutation) and `onClose()` back-to-back. From a user point of view the override clears correctly, but the user has no opportunity to review the defaulted values before persisting, no chance to Cancel out of a misclick, and the labelling is misleading (the button reads "Reset to song default", suggesting an in-form state change, not a confirmed mutation). The molecule's own JSDoc claims the spec'd two-step flow (`LineupEditor.tsx:11-15`) — the code contradicts its own contract. Fix: drop `onClose()` from `handleResetToDefault`; have `onReset` rewrite the form's `defaultValues` to `defaultLineup` and leave the dialog open until the user clicks Save (and have Save submit `{ lineupOverride: null }` when the working set equals the default and the entry started with an override). Update the LineupEditor JSDoc to reflect the chosen flow once decided.
- **Row 16 (FAIL — override badge truncated at 375 px).** Visual evidence: `18-override-badge-375.png` shows the badge rendering as `OVER` with an ellipsis. The badge is placed in the entry row's title column, which is set to a narrow width on mobile (the song title "Africa" is itself truncated to "Af…"). A reader on a phone sees a four-letter fragment that doesn't convey "override". Two fixes worth considering: (a) hoist the badge out of the truncated column so it sits next to the row index / chips instead of next to the song name; (b) shrink the badge text on mobile so the full word fits (e.g. shorten i18n string to `OVR` on `xs:` only — keep `OVERRIDE` on `sm:` and up). Option (a) is the cleaner fix because it preserves the semantic word at every viewport.
- **Row 18 (UNVERIFIABLE — backdrop-click).** The implementation choice (no backdrop dismiss) is reasonable for a destructive form (preserves typed data), but it is undocumented in the spec — the spec's "edge — modal accessibility" check asks the validator to _document what happens_. Documented: backdrop click does NOT close the dialog. ESC and the × / Cancel buttons do. agent-browser does not accept coordinate-based clicks (`agent-browser click` requires a ref or selector), so the only confirmation route was programmatic, which does not exercise the browser's native backdrop-click pathway.

## Verdict: FAIL
