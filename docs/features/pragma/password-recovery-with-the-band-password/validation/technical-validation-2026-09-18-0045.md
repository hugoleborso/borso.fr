## Notes

- **A20 / D13 — the recovery 429 copy contradicts the ratified spec, and the spec was not amended. This is the only FAIL, and the remedy is to change the spec, not the code.** The spec's *Error cases* reads: "429 `rate-limited`, rendered with the existing `auth.rateLimited` copy." The branch ships `auth.recoveryRateLimited` instead, and `login.core.test.ts:50` asserts the two keys differ.

  **The code's judgement is right and I endorse it.** `auth.rateLimited` reads *"Too many attempts — try again in a few minutes."* That sentence is true of the sign-in limiter, whose window is `RATE_LIMIT_WINDOW_MINUTES = 15`, and false of the recovery limiter, whose window the same spec sets at `SHARED_PASSWORD_WINDOW_MINUTES = 60` — a factor of four, told to a member who is already locked out and has no other way in. `recordAttempt` (rate-limit.utils.ts:61) opens a fresh window only once `nowMillis - windowStartedAt >= budget.windowMs`, so the wait really is up to the full hour from the first failure, and the new string — *"Too many attempts — try again in an hour."* — is the accurate one. Reusing the old key would have been the spec followed and the member misled. The spec asked for two things that cannot both be true.

  **What makes it a FAIL is not the copy, it is that nothing in the feature folder now describes what ships.** The spec's *Error cases* line and the plan's *Error cases* row both still say `auth.rateLimited`. The change is recorded only in `27e69ec`'s commit body, which is the right place to *announce* a deviation and the wrong place to *keep* it: a commit message is not the artefact the next reader opens, and after merge the spec is what a regression check, a follow-up feature or `/after-task-dantotsus` will read. A user-facing string the operator ratified one way and the branch ships another way, with the ratified document left standing, is exactly the drift this gate exists to catch — and rounding it up to PASS because the implementer's judgement was better would teach that a good reason is a substitute for amending the contract.

  **The fix is two lines and flips both rows.** In `spec/spec.md` *Error cases*, replace "rendered with the existing `auth.rateLimited` copy" with the recovery-specific key and say why the sign-in copy could not be reused; in `plan/plan.md`, update the *Error cases* row of the decision table to match. No code change. Re-run this validator afterwards.

- **A43 — `a4d78dc`'s "no behaviour change" is true for every response the endpoint can produce, and I checked rather than took it.** The old two-argument form consulted the response body first and only then the status; the new one reads the status alone. They diverge on pairs like `(500, { error: 'invalid-recovery' })` or `(401, { error: 'rate-limited' })`, where the old form answered from the body and the new one from the status — but the controller emits exactly five shapes (200; 400 from `zValidator`; 401 `{error:'invalid-recovery'}`; 429 `{error:'rate-limited'}`; 503 `{error:'auth-not-bootstrapped'}`), and on all five the two agree. The 400 case is the only non-obvious one: `zValidator`'s failure body is `{ success: false, error: { … } }`, whose `error` is an object, so the old `z.object({ error: z.string() })` guard already failed to parse it and both versions fell through to `auth.unknownError`. Recorded so nobody reads the commit's claim as broader than it is.

- **C06 — the `VotePage.test.tsx` flake looks genuinely fixed, and the fix is the right shape.** The previous run measured the retract case failing roughly one run in three; it now passes six isolated runs and three full `test:core` runs, nine consecutive greens. At the previously measured failure rate that outcome has probability ≈ (2/3)⁹ ≈ 2.6 %, which is evidence rather than proof, but it is the evidence the brief asked for. The change itself is the substantive part: `await flushMicrotasks()` became `await flushUntil(() => voteRow()?.getAttribute('aria-pressed') === 'true')`, and `flushUntil` (VotePage.test.tsx:70-78) alternates micro-task and macro-task flushes up to `FLUSH_ATTEMPTS_MAX = 8` and throws if the condition never holds. No early-exit false positive is possible in either direction: before the first click `aria-pressed` is already `'false'` and the wait is for `'true'`, and before the second click it is `'true'` and the wait is for `'false'`, so neither predicate is satisfied at entry. The one cost is diagnostic — a timeout now throws `the page never reached the state this case waits for` instead of an assertion diff naming the attribute — which is a fair trade for a deterministic gate.

- **The four security-relevant claims the brief named, all re-derived from the source at head rather than carried over.**
  - *Indistinguishability.* `recoverPassword` verifies the band password (credentials.service.ts:143-147) before it looks the username up (:148-149), and both failures return the single kind `{ kind: 'invalid-recovery' }`, which the controller renders as one status and one body (auth.controller.ts:79-81). It does **not** distinguish "this username exists" from "it does not", which is the property the spec actually asserts, and an attacker who can measure it already knows the answer from the one bit that matters.
