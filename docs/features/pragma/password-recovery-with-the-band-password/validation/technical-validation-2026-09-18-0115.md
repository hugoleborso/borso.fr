## Notes

- **D06 — the one edge case in the spec that no test exercises, and the one row where both earlier reports cited evidence that does not exist.** The spec's *Edge cases* says: *"The new password equals the old one. Allowed; the hash is rewritten with a fresh salt and the epoch still moves, which is what invalidates the other sessions."* Two behavioural claims live in that sentence — the request is not refused, and the epoch moves anyway — and neither is asserted anywhere in the Vitest suites.

  The `-0045` report passed this row on two citations, and I checked both. It said `it('clears the recovery budget once a recovery succeeds')` recovers "with the helper's default `newPassword`, which is `TEST_PASSWORD`, the password already on the row": the calls it means are auth.controller.test.ts:178-181, and they carry `sharedPassword: WRONG_SHARED_PASSWORD`, so they are the three 401s the case exists to count, not recoveries. It then said auth.controller.test.ts:186 "does the same and asserts 200": that call is `recoverPassword(app, { newPassword: NEW_PASSWORD, ipAddress })`, a different password. Every successful recovery in the suite — :77, :98, :120, :175, :196, :216 — passes `NEW_PASSWORD`. The helper's `newPassword ?? TEST_PASSWORD` default is only ever reached on calls that fail for another reason.

  **The behaviour itself is right, and is not in question.** `recoverPassword` never compares the new password with the stored hash — credentials.service.ts:143-155 goes verify, look up, `nextSessionEpoch`, `updateCredentialSecret`, `issueSession` with no equality branch — so the case is allowed by construction, and `/visual-validation` exercised it in a browser (its row 18, screenshot `09-same-password-recovery-1280.png`: recovered `marc` with his current password, then replayed his pre-recovery cookie and got 401). What is missing is the automated assertion. That distinction is the whole point of this category: a one-off browser pass is not a gate, and "allowed by construction" is a property of today's code, not a constraint on tomorrow's. A later change adding `if (await argon2Verify({ password: newPassword, hash: credential.passwordHash })) return { kind: 'invalid-recovery' };` — a plausible thing for someone to think is a security improvement — would pass all 159 back-e2e cases, all 1745 core cases, the 100 % coverage gate and the 100 % mutation gate, and would break a behaviour the operator ratified.

  **Remedy, roughly eight lines in `auth.controller.test.ts`**, beside the cases already there: sign one member in, capture the cookie, `await recoverPassword(app, {})` so the helper's `TEST_PASSWORD` default is the new password as well as the old, assert 200, assert the pre-recovery cookie is now refused, and assert `loginAsMember(app, 'tester', TEST_PASSWORD, <fresh ip>)` still returns 200. That pins both halves of the spec's sentence. Re-run `/technical-validation` afterwards; nothing else in this report needs revisiting.

  The alternative remedy — amending the spec to drop the edge case — is available and I do not recommend it. The sentence is the operator's answer to "must a locked-out member invent a new password?", and it is worth keeping true.

- **D12 is a PASS with a stated limit, not a rounding-up.** The spec says the short password is "refused by `zValidator` before any hashing, 400". The literal 400 through the router is not asserted for this route. I am counting the row covered because the behaviour the spec describes is pinned by a test plus a structural guarantee, and because the status is `@hono/zod-validator`'s contract rather than this feature's code; a reviewer who disagrees would want one more line in the back-e2e suite, in the same commit as D06's.
