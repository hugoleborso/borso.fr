## Notes

- A00: the plan is absent, so no row could be checked against a planned file list. Recommend `/technical-conception` before a third change of this size.
- Every sign-up for one concert now writes the same `session` row, so on Aurora DSQL any two that overlap conflict, and the client retries the loser whole after 100, 200, 400 and 800 ms with no jitter (database/client.ts, `CONFLICTED_WRITE_MAX_ATTEMPTS = 5`). If six fans press "Valider" within one transaction's span, do the colliding requests retry in step and leave the sixth with a 500 and the retry screen? This is inferred from the retry schedule and DSQL's optimistic concurrency, not measured; local Postgres serialises them instead. INVARIANTS names the price, but not how many simultaneous sign-ups it tolerates.
- The spec says people at one venue share an IP. The write budget is 60 a minute per client address per instance, and each fan spends two writes (sign-up and answers). Is a venue Wi-Fi with more than about 30 fans signing up in one minute on one instance expected to get "Too many tries at once"?
- `findOrImportSuggestedSongWithin` calls `withResolvedSpotifyTrack`, an HTTP call to Spotify, inside the open registration transaction (songs.service.ts). Is holding a transaction open across a third-party call acceptable here, given the transaction is retried whole on a DSQL conflict and would repeat that call?
- On a phone the message carries `max-md:order-last`, so it reads after the prize coupon rather than right under the venue (UC4). The commit message says this is deliberate to keep the prize above the fold. Whether it matches the validated mockups is for /visual-validation.
