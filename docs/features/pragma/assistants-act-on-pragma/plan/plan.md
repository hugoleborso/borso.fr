# Plan — assistants act on pragma through MCP and OAuth

> Early quality check. Pair with [`../spec/spec.md`](../spec/spec.md), [ADR-0041](../../../../adr/0041-pragma-serves-mcp-from-its-api-lambda.md) (MCP at `/mcp` on the API Lambda, stateless, `@modelcontextprotocol/sdk` behind `@hono/mcp`) and [ADR-0042](../../../../adr/0042-pragma-is-its-own-oauth-authorization-server.md) (pragma is its own OAuth 2.1 authorization server). When a defect lands and a Dantotsu traces back here, the chain is visible: the plan either named the risk and we missed mitigating it, didn't name the risk at all (planning gap), or named it correctly and the defect comes from elsewhere.

The takes and push branch this spec builds on has merged (`d117a320`, PR #193), so the sequencing condition in the spec holds.

## What the live workspace says that the spec did not

Read from `apps/pragma/` on 2026-10-27, before writing the rows below.

- **Production serves only `/api/*` from the API.** `StaticSite` adds one CloudFront behaviour, `props.api.pathPattern ?? '/api/*'` (`infra/cdk/src/constructs/static-site.ts`), and the default behaviour is the S3 site with an SPA fallback. So `https://pragma.borso.fr/mcp`, `/oauth/token` and `/.well-known/oauth-*` would answer `index.html` today. The construct needs a list of API path patterns. That is an `infra/cdk` change under the 100% coverage gate. `infra/shared` does not use `StaticSite`, so the `borso-shared` template does not move and no `shared-deploy` dispatch is owed.
- **Previews serve the API on its own host** (`previewApiHostname`, `infra/cdk/src/internal/naming.utils.ts`) and the site on the previews CDN. So the issuer and the `/mcp` URL are the site origin in production and the API host on a preview. The API cannot derive this from the request: CloudFront forwards with `ALL_VIEWER_EXCEPT_HOST_HEADER`, so `Host` is the API Gateway host. Both origins come in as environment variables set by the stack.
- **API Gateway HTTP API buffers responses** (`docs/knowledge/apigw-http-api-has-no-response-streaming.md`). The stateless transport runs with `enableJsonResponse: true`, so every answer is one JSON body and never an SSE stream. `GET /mcp` answers 405.
- **`DEFAULT now()` is refused** outside an allow-list by `apps/pragma/api/src/database/migrations.audit.test.ts`. The spec's DDL uses it on two columns. The migration drops the defaults and the services pass `now`.
- **pragma's layer-marker budget is zero** (`docs/standards/convention-baseline.json` has no `layer-marker:pragma` entry, and the architecture section of CLAUDE.md says the invariant holds fully in pragma). The spec's `mcp/tools/<area>.tools.ts` has no layer suffix and would fail `convention-drift.ts --check`. See D1.
- **zod is 3.25.76** in `apps/pragma/node_modules`, which satisfies the `^3.25 || ^4.0` peer range of `@modelcontextprotocol/sdk@1.32.2` and `@hono/mcp@0.3.2`. The SDK's own OAuth schemas are written against `zod/v4`.
- **`@hono/mcp@0.3.2` declares `hono-rate-limiter` as a required peer** with no `peerDependenciesMeta`, and `.npmrc` sets `auto-install-peers=true`, so pnpm installs it transitively. Only `mcpAuthRouter` in `@hono/mcp/auth` imports it, dynamically. We never import `@hono/mcp/auth` (see D3), so it is installed but never loaded.
- **Session gate is cookie-only.** `requireMemberSession` (`apps/pragma/api/src/auth/member-session.middleware.ts`) reads `pragma_session`, and `judgeMemberSession` compares the cookie's epoch with `member_credential.session_epoch`. A grant reuses that epoch rather than a new "credential version" (see D4).
- **`RequireSession` keeps only `location.pathname`** when it sends a visitor to `/login` (`apps/pragma/site/src/components/organisms/RequireSession.tsx`). The consent page carries the whole authorization request in its query string, so the query string would be lost on sign-in. The gate has to keep `pathname + search`.
- **About 110 routes are mounted** in `apps/pragma/api/src/app.ts` across 22 routers. Each HTTP controller maps a service outcome `kind` to a status and answers `{ error: kind }`. A tool answers the same `kind` as its error code, so the two cannot disagree on the code.

## Decisions taken while planning

Code-level choices the spec leaves open. None changes what a member sees beyond what the spec describes, except D2, which is listed so the operator can overturn it.

| # | Decision | Why |
|---|---|---|
| D1 | Each bounded context owns its tools in `<domain>/<domain>-tools.controller.ts` (for example `songs/songs-tools.controller.ts`), beside its HTTP controller. `mcp/` holds only the transport, the bearer gate's use, the registry and the result shaping. | `.tools.ts` is not a layer suffix and pragma's layer-marker budget is zero. A tool validates input, calls one service and shapes the answer, which is the controller role. Keeping it in the domain folder keeps the slice vertical and puts the tool's refusal handling next to the route's. |
| D2 | Routes with no tool, listed in `mcp/tool-coverage.core.ts` with a reason each: health, `/api/auth/*`, `/api/admin/*`, `/api/__test/*`, `/api/audience/*`, `/api/uploads/*`, `/api/offline-manifest`, `/api/oauth/*`, `/api/assistant-grants/*`, `PUT /api/me/password`, `/api/me/passkeys*`, `/api/me/calendar-feed`, `/api/notifications/subscriptions`, `/api/notifications/vapid-public-key`; and since 2026-10-29 the routes D14 takes away from assistants. | The spec names the first five groups. The rest are credentials (password, passkeys, the secret calendar feed address, the grants themselves) or bound to one browser (push subscription, VAPID key, offline manifest). An assistant changing the member's password would also end its own grant. |
| D3 | Do not use `mcpAuthRouter`, `bearerAuth` or `ProxyOAuthServerProvider` from `@hono/mcp/auth`. Reuse the SDK's `OAuthClientMetadataSchema`, `OAuthMetadata`, `OAuthProtectedResourceMetadata` and `OAuthTokens` types, and its OAuth error classes for the error bodies. | Its rate limiter is in memory (useless across Lambda instances) and needs a third package; its `bearerAuth` builds `resource_metadata` from the request URL, which is the API Gateway host behind CloudFront; it does not fit the controller, service, repository triad or its coverage gate. ADR-0042 already chose to own the endpoints and reuse the schemas. |
| D4 | The grant column is `session_epoch`, compared with `member_credential.session_epoch`, instead of the spec's `credential_version`. | The word already exists in `VOCABULARY.md` (Sign-in session) and in `judgeMemberSession`; a second name for the same number is the drift the vocabulary exists to stop. |
| D5 | `assistant_grant` gains `refresh_family_hash text NOT NULL UNIQUE`. A refresh token is `<family>.<secret>`: the family is minted once per grant and kept across rotations, the secret is new on every rotation. | Replay detection needs to recognise every token the grant ever rotated away, not only the last one: a thief who refreshes twice would otherwise leave the first token unrecognised and keep the grant. Matching on the family needs one column and no table of retired hashes; a token of the family that is not the current one is a replay. Only a holder of some token of the grant knows the family, so nobody else can revoke it by guessing. (Revised after technical validation 2026-10-27-1234, which found the first choice, `previous_refresh_token_hash`, missed a replay two rotations old.) |
| D6 | Authorization is two steps. `GET /oauth/authorize` (API, public) validates the client, the redirect URI and PKCE, then redirects to the site's `/oauth/consent` with the same query. The consent page reads `GET /api/oauth/consent` and posts `POST /api/oauth/consent` (both cookie-gated, typed through `hc`), which answers `{ redirectTo }`; the page then navigates there. | The consent page needs the member session, which only the `/api` routes see through the `hc` client, and keeping the request in the query string needs no pending-request table. The API re-validates every parameter on the POST, so the query string is never trusted. |
| D7 | Requested scopes other than `pragma` are ignored, and the token response states `scope: "pragma"`. A `resource` parameter must equal `<issuer>/mcp` when present. | Vibe sends `scopes = ["pragma"]`; other clients may send nothing or ask for `offline_access`. RFC 6749 §3.3 lets the server issue a different scope than requested. Refusing would break a client for no security gain, since there is only one scope. |
| D8 | Clients with no grant, created more than 30 days ago, are deleted when a new client registers. No scheduled job. | ADR-0042 promises the sweep; a cron is a recurring job nobody asked for (CLAUDE.md, Don'ts). Registration is the only thing that grows the table. |
| D9 | `last_used_at` is written at most once every 5 minutes per grant. | Every tool call otherwise writes the same row, and two concurrent calls conflict under DSQL's optimistic concurrency. The monthly output metric needs day precision, not seconds. |
| D10 | Tool results are one `text` content block carrying a compact JSON projection made for an assistant, not the HTTP body. A read answers ids plus the fields the next step needs, names instead of ids where a person would say a name (who plays what, the song of an entry, the assignee of a task), dates as ISO strings and no audit timestamps; a `detail` flag adds the long fields where they are sometimes needed (`get_song` adds the chord chart and links). A write answers a short confirmation: `{ id }` for a creation, `{ id, updated: [fields] }` for a change, `{ id, deleted: true }` for a deletion, plus a value the next step needs (`request_take_upload` its upload address, `cast_vote` the points left). Every answer is serialized by `serializeCompactly` (`mcp/tool-result.core.ts`), which leaves out any field that is null, missing or empty text, so an absent field reads as empty. Long lists take `limit` and `cursor` and answer `total` and `nextCursor`. Refusals stay `isError: true` with `{ error: <kind> }`, the route's own code. No `outputSchema`. | *Revised 2026-10-28 after the operator's preview trial.* The first version answered the route's body, which is shaped for the screens: `search_songs` returned every song with its whole chord chart and lineup ids, about 1,500 characters per song (9,156 for the 6 songs of the preview fixture), and a typical task needed three to eight calls that each re-read it. Measured on the preview fixture (6 songs, 4 members, 5 instruments, 3 takes) over ten scripted band tasks: 42 calls and 104,194 characters (about 26,000 tokens at 4 characters per token, an estimate) before, 13 calls and 7,763 characters (about 1,900 tokens) after. The largest answer went from 9,156 characters (`search_songs`) to 1,796 (`get_session`, a whole concert with its setlist and lineups). `mcp/tool-budget.test.ts` holds these numbers as budgets so they cannot creep back. The production row counts could not be read from this session (`scripts/db-read.sh` times out on port 5432), so the per-row sizes above are the ones to scale. |
| D11 | Every tool that takes a song, member, instrument, setlist, bar, task or improvement takes a reference: its id, or its name written in any case and with or without accents. An exact name wins; otherwise a name the reference is part of; several matches answer `{ error: '<noun>-ambiguous', candidates: [{ id, label, hint }] }` (at most 10, with `more`), none answers `<noun>-not-found`. A session takes its id, `next`, `next-concert`, `next-practice`, `last` or a day `YYYY-MM-DD` read in Paris time. A setlist entry takes its id, its song's id or its song's title. Lineups are written as `{ "<member>": "<instrument>" \| ["<instrument>", …] \| null }` with names or ids. Matching is pure (`helpers/reference/reference.core.ts`, `sessions/session-tool.core.ts`, `setlists/setlist-tool.core.ts`); a refusal is thrown as `ToolRefusedError` from the service and answered by the adapter like any other refusal, never reported as a failure. | Songs, members, instruments and setlists are a handful of rows a band names out loud; resolving by name removes the list call every task started with. A UUID is used as given without loading anything, so an unknown id still answers the route's own `not-found`. Throwing keeps the dozens of resolutions out of every controller; only the MCP adapter catches it. |
| D12 | Fewer, wider tools: reads that answer a task in one call and writes that take a batch. `get_session` answers the session with its setlists, their entries in order with song titles and who plays what; `get_setlist` the same for one setlist; `create_setlist` takes `session` and `songs`; `add_setlist_entries` and `remove_setlist_entries` take lists; `reorder_setlist` takes a whole `order`, a `move` to a 1-based position, or a `swap`; `comment_on_take` and `get_take` take a song for its latest take; `list_tasks` filters by assignee (`me`), song and status. Near-duplicates merged: `set_default_lineup` into `update_song`, `set_entry_lineup` into `update_setlist_entry`, `list_session_setlists` into `list_setlists`, `list_setlist_entries` into `get_setlist`, `get_closing_proposal` into `get_vote_board`, link and unlink into `link_setlist`, the two improvement vote tools into `vote_on_improvement`, `undo_study` into `log_study` (`undo: true`), set and delete of a mastery score (`score: null` deletes), `get_transition_comment` and `delete_transition_comment` into `list_transition_comments` and `set_transition_comment` (`comment: null` deletes), `list_member_instruments` into `list_members`, `list_take_comments` into `get_take`, `list_mastery_overrides` and `get_mastery_history` into `get_song_mastery`. 87 tools became 73; every route keeps a tool and D2 is unchanged. A tool now names the routes it covers (`routes`, one or more), which `mcp/tool-coverage.test.ts` checks both ways. | Each merge is a pair of tools an assistant had to choose between for one intent. Song mastery tools sit in the songs slice (`get_song_mastery`, `set_song_mastery`) and `get_session` in the setlists slice, because the services they compose would otherwise import each other in a cycle (`import/no-cycle`). The setlist composites live in `setlists/setlists-tools.service.ts` so `setlists.service.ts` stays under the 300-line limit. |
| D13 | The adapter serves `tools/list` itself: the same JSON schema the SDK builds from each tool's Zod schema, without `$schema`, without `additionalProperties: false` (Zod strips unknown keys rather than refusing them, so the mark was not even true) and without the SDK's default `execution` field. It went from 46,737 characters (about 11,700 tokens, estimate) for 87 tools to 32,730 (about 8,200 tokens) for 73. `toJsonSchemaCompat` is the SDK's own converter, reached through its `./*` export, so no dependency is added. |
| D14 | The operator's list of 2026-10-29: 35 tools. `save_<noun>` replaces `create_<noun>` and `update_<noun>` for sessions, setlists, songs, bars, improvements and tasks: without a reference it creates, and a creation missing a required field answers `{ error: 'invalid-input', fields }` (`parseToolFields` in `mcp/mcp.service.ts`, `describeInvalidFields` in `mcp/tool-refusal.core.ts`); with a reference (id or name, D11) it changes only the fields given. ### Pattern Coherence pass

- **New dependencies:** `@modelcontextprotocol/sdk` and `@hono/mcp`, both ratified by ADR-0041, pinned exactly in the catalog. `hono-rate-limiter` arrives as an auto-installed peer and is never imported (D3). No other dependency: PKCE and token minting use `node:crypto`, not the transitively present `pkce-challenge`.
- **Rate limiting:** one pattern exists (database buckets, `auth/rate-limit.utils.ts`, client address from `client-address.environment.ts`). Registration reuses it with a new budget rather than the in-memory limiter `@hono/mcp/auth` ships.
- **Authentication gates:** two after this feature, `requireMemberSession` (cookie) and `requireBearerSession` (token). They share `readMemberId` and the epoch rule; the bearer gate sets the same context key so a service never knows which door was used. Deliberate: cookies cannot work for a terminal client, and tokens should not work in the browser app.
- **Zod:** the app stays on `zod` 3.25 (`catalog:zod3`). The SDK's schemas come from its `zod/v4` import and are only used through `.safeParse` in `oauth.schema.ts` and as types, never mixed into a pragma `z.object`.

## Risk register

| Risk | Severity | Mitigation in plan | Detection if it slips |
|---|---|---|---|
| A production token works on a preview, or a preview reads production grants | high | Three tables in `SECRET_TABLES_BLOCKED_ON_PREVIEW`; issuer per stage | `stack.test.ts` blocklist assertions; template snapshot diff |
| Open redirect from `/oauth/authorize` | high | Redirect only to a URI registered by that client, matched by `matchesRegisteredRedirectUri`; unknown client or URI answers JSON 400, never a redirect; the consent POST re-validates | Core table test; e2e with an unregistered `redirect_uri` asserts status 400 and no `Location` header |
| Authorization code stolen and redeemed without the verifier | high | PKCE S256 mandatory; code bound to `client_id` and `redirect_uri`; one use, 60 s | e2e with a wrong verifier → `invalid_grant`; Stryker on `oauth.core.ts` |
| Raw token stored, so a database read leaks live credentials | high | Only SHA-256 hashes stored; the reader blocklist also hides the tables from agents' read-only production access (ADR-0044) | e2e scans the rows for the raw values |
| A grant outlives a password change or member deletion | high | `judgeGrant` on every bearer call and refresh; member deletion deletes grants in the same transaction | e2e cases listed above |
| A tool bypasses a rule the route enforces because the controller holds logic the tool skips | medium | Tools call the same service function as the route; a controller holding logic is already against the clean-code rule, so any found is moved into the service in the same slice | Per-area e2e asserts the same database change as the route test; `/technical-validation` reads each tool next to its route |
| A route lands later with no tool, or a tool keeps a dead route | medium | `tool-coverage.test.ts` with `staleExclusions` | The test, in back-e2e on every push touching pragma |
| zod 3 schemas lose detail in the SDK's JSON Schema conversion (refinements, transforms) so assistants send wrong shapes | medium | Merge only `ZodObject` schemas; where a route schema is an effect, the tool states the object and the route's refinement runs inside the service or the schema's `superRefine` | Coverage test also asserts every tool's listed `inputSchema` has the properties of its route's schema; e2e calls one tool per area |
| `zod/v4` from the SDK and pragma's zod 3 meet in one type and fail `tsc` | low | Pattern Coherence rule: SDK schemas used only through `safeParse` and types | `pnpm --filter @borso-app/pragma typecheck` |
| Bundle growth or cold start from the SDK (it lists `express`, `ajv` and others as dependencies) | medium | Import only `@modelcontextprotocol/sdk/server/mcp.js`, `/shared/auth.js` and `/server/auth/errors.js` so esbuild tree-shakes the rest; no import of the client or Express transports outside tests | `pnpm run synth` asset size compared before and after in the PR; not measured yet, and the ADR's "cache the registry at module level" is the fallback |
| ESM Lambda cold-start failure from a CommonJS dependency inside the SDK | medium | Existing `createRequire` banner in `LambdaApi` | Preview smoke: `POST /mcp` `initialize` answers 401 (not 502) on the preview API host |
| The DCR endpoint fills the table | medium | 10 per hour per address; sweep on registration (D8) | `OAuthRegistrationRateLimited` alert; e2e |
| Two concurrent refreshes from one client count as a replay and revoke the grant | low | Accepted by the spec ("replaying an old one revokes the whole grant"); clients serialise refresh | `OAuthTokenReplay` in Sentry; the member re-authenticates |
| `last_used_at` writes conflict under concurrent tool calls | low | D9 throttle; the write is outside the tool's transaction and a conflict is swallowed and logged | e2e with two parallel calls both succeed |
| CloudFront pattern change removes or reorders the existing `/api/*` behaviour on other apps | medium | Default stays `['/api/*']`; existing apps pass nothing | Template snapshots of the other apps unchanged in the diff; `infra/cdk` coverage at 100% |
| Consent query lost at sign-in | medium | `RequireSession` keeps `search` | `login.core.test.ts`; visual validation signed-out path |
| A route the spec did not foresee is excluded and a member expected it (D2) | low | Every exclusion has a written reason in `TOOL_EXCLUSIONS` | Operator review of D2 in the PR |
