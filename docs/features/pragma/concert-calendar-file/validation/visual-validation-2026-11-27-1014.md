## Notes

- Row 16. The spec's reason for the tap is that "the phone offers to add it to the calendar app". That is iOS Safari or Android behaviour on a `text/calendar` attachment, and no real phone or simulator is reachable from the sandbox. What a browser can show passed in row 15: same tab, page kept, correct file delivered. It needs a check on a real phone against the preview.
- Row 32. A path segment that is not a UUID answers `400` with a serialised `ZodError` (`"format": "guid"`, the regex, `"path": ["sessionId"]`), not `422 not-an-upcoming-concert`. The spec says "an unknown id answers 422" without saying whether a malformed id counts as an id, so this row is ambiguous rather than failed. For comparison, the sign-up route also answers a malformed body with a 400 `ZodError` (measured with `POST …/concerts/<practice id>/registrations` and `{}`), so the calendar route matches the sign-up's existing behaviour for malformed input.
- Rows 25, 29, 30, 27. The local seed holds one upcoming concert and nothing else. To reach these cases, a practice, a past concert and a later concert were created through `POST /api/sessions` as `hugo`, the later concert's message was set through `PATCH …/announcement`, and its venue was set to null with a direct `UPDATE session SET venue = null` on the local dev database, since the API refuses an empty venue. All three sessions were deleted through `DELETE /api/sessions/:id` afterwards. The sign-up of "Camille" on the seeded concert remains in the local database.
- Row 18. The probe exhausted the read bucket of this address for one minute, which also blocks `/upcoming` from the page for that minute. It was run last for that reason.

## Verdict: PASS_EXCEPT_UNVERIFIABLE
