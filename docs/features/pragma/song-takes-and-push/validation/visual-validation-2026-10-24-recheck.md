## Notes

- **49: argent's `tap` is not a touch event on Chromium.** Before each argent tap I put capture-phase listeners on the document. Every argent `gesture-tap` arrived as `pointerdown` and `click`, both with `pointerType: "mouse"`, and there was no `touchstart` at all. argent 0.22.1's tool-server (`dist/tool-server.cjs`, `sendTouch`) sends `Input.dispatchTouchEvent` only for two-point gestures. A single point is sent as `Input.dispatchMouseEvent` `mousePressed`/`mouseReleased`. argent's browser also reported `innerWidth` 500 × `innerHeight` 669, `maxTouchPoints` 0 and `(pointer: coarse)` false, because headless Chromium ignored `--window-size=375,812`. So the argent taps prove only that each control is reachable by a click at its normalised coordinates. The PASS on each 49 row comes from the second pass. That pass ran in the same browser and set `Emulation.setDeviceMetricsOverride` to 375 × 812 mobile and `Emulation.setTouchEmulationEnabled` to 5 points, which gave `maxTouchPoints` 5, `(pointer: coarse)` true and `(hover: none)` true. It then tapped each target with `Input.dispatchTouchEvent` `touchStart`/`touchEnd`, and every target logged `touchstart`, `touchend` and a `click` with `pointerType: "touch"`. `docs/knowledge/real-touch-gestures-over-cdp.md`, `docs/knowledge/driving-previews-with-agent-browser-and-argent.md` and the `scripts/argent.sh` banner all say `gesture-tap` is a real touch event on Chromium. That is false for argent 0.22.1, and I logged it to the kaizen log.
- **49b, an observation that is not a row.** The timeline mark's hit area is 12 × 24 px (`w-3 h-6`). The tap at its centre landed, but it is the smallest touch target among the five, and a thumb aimed a few pixels to either side lands on the bare track. With several comments close together the marks overlap.
- **50.** Headless Chromium with the fake microphone always produced audio, so I could not get an empty recording from a real cut. I replaced each chunk with an empty `Blob` at the `MediaRecorder` event boundary. Everything from `recorder.adapter.ts` onward ran unmodified. The other half of `acf846f0`, where the queue marks an *already stored* empty entry as failed without contacting the network, was not driven in the browser. It is covered by `take-queue.store.test.ts` and `take-queue.core.test.ts` only.
- **46c/46d.** The edit form saves optimistically and navigates to the song page before the 409 arrives. So the member sees the refusal at the top of the song page, which opens at `scrollY` 0, rather than beside the edit form's Save. It is in view at both widths. The edit form's own slot above Save only shows on a failure that happens before navigation, and this run did not produce one.
